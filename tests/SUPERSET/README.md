# Pruebas del agente · gestor de paneles

Circuitos que conversan con el agente real desde la terminal, conectados como el cliente del frontend. Comprueban en Superset QA lo que quedó guardado y un juez LLM valora cada respuesta. Al final dejan un reporte en `reports/`.

La guía para prepararlos, correrlos y agregar más está en [docs/SUPERSET/SUPERSET_AGENT_TESTS.md](../../docs/SUPERSET/SUPERSET_AGENT_TESTS.md).

## Comandos

Los argumentos van después de `--`. Ningún comando de `--list` se conecta a nada.

```bash
# Antes de correr: ver qué hay y qué expectativas no tienen respaldo (auditoría), sin conectarse
npm run test:agent:superset -- --list
npm run test:agent:superset:productive -- --list

# Para iterar sobre un arreglo: un circuito, o varios separados por comas (minutos, no horas)
npm run test:agent:superset -- --circuit bars-3
npm run test:agent:superset -- --circuit bars-3,lines-1

# Un grupo, o varios
npm run test:agent:superset -- table
npm run test:agent:superset -- pivot heatmap mixed funnel     # requieren los gráficos base del desarrollador

# Medir estabilidad antes de dar algo por arreglado (cada circuito 3 veces)
npm run test:agent:superset -- --circuit bars-3 --repeat 3

# Pruebas productivas (ver "Pruebas productivas", al final)
npm run test:agent:superset:productive -- ventas
npm run test:agent:superset:productive -- --circuit prod-3328

# Todo (entre 60 y 90 minutos; mejor por grupos)
npm run test:agent:superset

# Otro modelo u otro proveedor: CLIENT_TEST_MODEL decide (gpt-… u o… → OpenAI; gemini-… → Gemini)
CLIENT_TEST_MODEL=gpt-5-mini npm run test:agent:superset -- --circuit bars-1

# O el menú, para todos los servicios
npm run test:agent
```

| Opción                          | Qué hace                                                                                                                                                                            |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<grupo> …`                     | Solo esos grupos (`bars`, `lines`, `table`, `pie`, `big_number`, `card`, `pivot`, `heatmap`, `mixed`, `funnel`, `guided`, `limits`; en las productivas, `validaciones` y `ventas`). |
| `--circuit <id>[,<id>…]` (`-c`) | Solo esos circuitos, por su id.                                                                                                                                                     |
| `--repeat <n>` (`-r`)           | Cada circuito n veces: el reporte suma la estabilidad.                                                                                                                              |
| `--list`                        | Grupos, circuitos y hallazgos de la auditoría, sin correr nada.                                                                                                                     |
| `--help` (`-h`)                 | El uso.                                                                                                                                                                             |

**Al terminar:** en `reports/` quedan un reporte por circuito, con su id (`bars-1.md` y `bars-1.json`), que se sobrescribe en cada corrida de ese circuito, y el resumen de la última corrida (`_current_run.md`). El `.md` es para leer: empieza por "Pasos a revisar". El `.json` tiene cada turno completo y la configuración del gráfico antes y después de cada paso. El código de salida es `0` si todo chequeo estricto pasó, `1` si alguno falló y `130` si se interrumpió con Ctrl+C. Con Ctrl+C se borran los gráficos creados y se restauran los base.

## Circuitos disponibles

Cada circuito es una conversación nueva sobre un solo gráfico. Los grupos siguen las familias de gráfico de [SUPERSET_CHART_LIMITS.md](../../docs/SUPERSET/SUPERSET_CHART_LIMITS.md) [[2]](../../docs/SUPERSET/SUPERSET_CHART_LIMITS.md#2-lo-que-sí-se-puede-cambiar); el grupo `limits` reúne lo que no se puede hacer ([[3]](../../docs/SUPERSET/SUPERSET_CHART_LIMITS.md#3-lo-que-no-se-puede-cambiar)). El gráfico sale de uno de dos lugares:

- **Lo crea el agente** en el sandbox (`SUPERSET_TEST_DASHBOARD_ID`), y al final se borra. No requiere intervención. En los circuitos "de producción", la prueba además lo **prepara** en Superset con lo que el agente no crea: una métrica y un filtro con fórmula SQL y un rango de fechas (y, en la tabla, una regla de formato). Así los cambios se prueban sobre un gráfico con configuración que no debe perderse.
- **Gráfico base del desarrollador:** tabla dinámica, mapa de calor, combinado y embudo, que el MCP no crea. Ver ["Gráficos base"](#gráficos-base-intervención-del-desarrollador). La prueba guarda su configuración al empezar y la restaura al terminar; nunca los borra. Si falta alguno, su circuito se omite y la corrida dice qué hacer.

Cada circuito escribe sus datos tal como los diría un usuario: su dataset y los nombres reales de sus métricas y columnas, repartidos entre los tres datasets que el agente tiene precargados. Para escribir una prueba nueva, mira la guía en [SUPERSET_AGENT_TESTS.md](../../docs/SUPERSET/SUPERSET_AGENT_TESTS.md#3-agregar-circuitos).

## Gráficos base (intervención del desarrollador)

Solo hacen falta para `pivot-1`, `heatmap-1`, `mixed-1` y `funnel-1`. Se preparan una vez:

1. **Un segundo dashboard sandbox,** distinto del de los circuitos, con "E2E" en el título y cuyo dueño incluya a la cuenta del asistente (`MET_BOT_PAY`). Su id va en `SUPERSET_TEST_BASE_DASHBOARD_ID` del `.env`. Es otro dashboard para que los mensajes de los demás circuitos ("pon la leyenda abajo") no se vuelvan ambiguos.
2. **En ese dashboard, un gráfico de cada tipo,** creado a mano en Superset sobre el dataset `ACCOUNT_MOVEMENTS_VIEW`, con `MET_BOT_PAY` entre sus dueños (si no, el agente responde que pertenece a otros usuarios):

   | Gráfico base      | Tipo en Superset       | Cómo se arma                                                                                                                                  |
   | ----------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
   | Tabla dinámica    | Pivot Table            | `MEDIO_VALIDACION` en filas, sin columnas, la métrica `Total recaudo por ventas`, agregación Sum, sin totales.                                |
   | Mapa de calor     | Heatmap (`heatmap_v2`) | Eje X: `DATE`, con intervalo de tiempo Month. Eje Y: `MEDIO_VALIDACION`. Métrica: `Total recaudo por ventas`. El resto por defecto.           |
   | Gráfico combinado | Mixed Chart            | `DATE` en el eje X por mes; consulta A: `Total recaudo por ventas` en línea; consulta B: `transacciones` en línea; ambas en el eje principal. |
   | Embudo            | Funnel Chart           | `MEDIO_VALIDACION` como etapas, la métrica `Total recaudo por ventas`; el resto por defecto.                                                  |

   **Ojo con el mapa de calor:** en la galería de Superset hay varios con nombre parecido. El correcto es **Heatmap**, de la categoría de correlación, cuyo editor tiene eje X, eje Y y métrica. **No sirve "deck.gl Heatmap":** es un mapa geográfico, y su editor pide ubicación (Spatial) y peso (Weight), pero no tiene eje Y. Si la prueba encuentra uno de esos en el dashboard base, lo dice al empezar.

   El título es libre. La prueba encuentra cada gráfico por su tipo, así que debe haber uno solo de cada tipo en ese dashboard.

La especificación de cada uno está en `BASE_CHARTS` ([fixtures.ts](fixtures.ts)): si cambia, actualiza esta tabla. Si una corrida se corta sin poder restaurar un gráfico base, el resultado lo dice; vuelve a armarlo como indica la tabla.

## Casos y resultado esperado

Todos los circuitos con gráfico del agente empiezan creándolo y terminan borrándolo, salvo donde la tabla diga otra cosa:

- **Creado:** se crea, se agrega al sandbox y el agente lo confirma.
- **Borrado:** borrado definitivo, avisando que no se puede deshacer.

Esos dos pasos no se repiten abajo. Los circuitos sobre un gráfico base no crean ni borran nada.

| Resultado       | Qué comprueba la prueba en Superset                                             | Qué valora el juez en la respuesta                                                            |
| --------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **Aplicado**    | Se guardó lo pedido y nada más cambió.                                          | Que confirme el cambio sin inventar otros.                                                    |
| **No aplicado** | No escribió nada y el gráfico quedó igual.                                      | Que diga que no se puede (o no así), por qué, y ofrezca lo más cercano que sí, sin aplicarlo. |
| **Pregunta**    | No escribió nada, y la respuesta hace una pregunta.                             | Que pregunte lo justo, con opciones claras.                                                   |
| **Quitado**     | Salió del dashboard y el gráfico sigue existiendo (la prueba lo borra después). | Que avise que el gráfico sigue existiendo.                                                    |

Notas de lectura:

- **Valores por defecto:** "Aplicado" cuenta lo que el gráfico muestra. Una opción que nunca se guardó vale su valor por defecto de Superset (por ejemplo, las etiquetas de la circular ya van por fuera), así que pedirla no exige escribirla.
- **"Antes, la prueba…":** la prueba dañó o preparó el gráfico directamente en Superset, como si alguien lo hubiera editado ahí; el usuario solo describe lo que ve.
- **Intervención:** "—" no requiere nada del desarrollador. Si no, dice qué gráfico base crear a mano en Superset y de qué tipo. Cómo se arma cada uno está en ["Gráficos base"](#gráficos-base-intervención-del-desarrollador).
